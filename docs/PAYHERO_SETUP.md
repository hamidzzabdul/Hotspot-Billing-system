# Pay Hero payments

The payment gateway is Pay Hero Kenya v2. Direct Safaricom Daraja integration has been removed. Pay Hero's STK endpoint still uses M-Pesa as the underlying mobile-money rail (`provider: "m-pesa"`); collection is managed entirely through Pay Hero, without Daraja consumer keys or passkeys in Wifex.

## Server configuration

Keep these in `backend/.env`, never frontend variables or source code:

```dotenv
PAYMENT_MODE=disabled
PAYHERO_AUTH_TOKEN=
PAYHERO_CHANNEL_ID=
PAYHERO_CALLBACK_SECRET=
PUBLIC_API_URL=https://wifi.example.com
```

- **Auth token:** Copy the Basic Authorization token from **Pay Hero → API Keys**. You can paste either the token alone or `Basic <token>`; Wifex normalizes the prefix. [Official authorization guide](https://docs.payhero.co.ke/docs/authorization).
- **Channel ID:** The numeric ID under **Payment Channels → My Payment Channels** for the account you collect into. [Official collection endpoint](https://docs.payhero.co.ke/docs/post-initiate-mpesa-stk-push-request).
- **Callback secret:** Generate a separate random secret, at least 32 characters. This is generated by you, not issued by Pay Hero.
- **Public API URL:** Your public HTTPS origin. Wifex sends the callback URL `PUBLIC_API_URL/api/payhero/callback/PAYHERO_CALLBACK_SECRET` with each payment request.

Once those values and the existing `ENCRYPTION_KEY` are configured, explicitly change `PAYMENT_MODE=live` and restart the backend. Startup validates the settings. The default remains disabled. Adding keys alone does not silently enable payments.

## Payment flow

1. The backend reads the plan price and creates an idempotent purchase.
2. It sends the amount, normalized phone, channel ID, application reference, and callback URL to `POST https://backend.payhero.co.ke/api/v2/payments` using server-side Basic Auth.
3. The returned Pay Hero `reference` is stored separately as `providerReference`; `CheckoutRequestID` remains separately stored. The application reference is never overwritten.
4. Callbacks use Pay Hero's documented `response` envelope. They are persisted before acknowledgement, then checked against the application reference and checkout ID.
5. Before granting access, the worker independently calls the authenticated transaction-status endpoint using the **Pay Hero reference**, checks the returned reference/provider/status/receipt, and verifies callback amount, phone, and receipt. Duplicate callbacks still create one access pass.
6. The billing worker checks outstanding provider references automatically (first after 15 seconds, then at 30-second intervals). **Check with M-Pesa** also allows an operator to recover a missed callback by settling a trusted successful status response with a verified receipt. `QUEUED` remains pending. A provider timeout stays reviewable and does not cause an automatic second charge.

See the official [callback format](https://docs.payhero.co.ke/docs/payment-callback) and [transaction-status API](https://docs.payhero.co.ke/docs/get-transaction-status).

## Existing records and testing

Existing history is preserved. Old records without a Pay Hero gateway/reference are treated as legacy and are never sent to Pay Hero for reconciliation. Old callback inbox events are not processed by the Pay Hero worker. Review outstanding legacy transactions with their original provider.

Automated tests use an isolated MongoDB replica set and controlled Pay Hero responses; no credentials or external payment requests are used. Runtime simulation is not supported; controlled adapters are confined to automated tests. Pay Hero Kenya v2's documented host is a production service; this app does not invent a sandbox endpoint or mode. Validate the live account/channel and callback behavior using provider-approved testing before accepting customer payments.

## Local HTTPS callbacks

For a locally hosted installation, keep the application on its LAN/local URL and expose only the restricted callback relay:

```sh
npm run callback:relay
ngrok http 4001 --inspect=false --log=stdout --log-level=warn
```

Run these in separate terminals and leave them running. The relay binds to `127.0.0.1:4001` and forwards only the exact secret callback POST to the API on `127.0.0.1:4000`. Application, account, and administration routes return 404. `/health` provides a non-sensitive reachability check. The relay does not forward cookies or browser authentication headers. Request inspection is disabled to avoid capturing callback bodies and secret paths in the local inspector.

Set `PUBLIC_API_URL` in `backend/.env` to the tunnel's public HTTPS origin (without a trailing slash), set `PAYMENT_MODE=live`, then restart `npm run start:local`. The relay reads the same callback secret as the app. When the tunnel URL changes, update this origin and restart the app before accepting another payment. The computer, application, relay, and tunnel must stay running for public callbacks. A fixed HTTPS deployment is preferable for unattended service.

## Authorized live verification

After validating the collection channel and public callback reachability, an operator can explicitly send a real **KES 1** verification payment:

```sh
node scripts/verify-payment.mjs YOUR_AUTHORIZED_MPESA_NUMBER
```

This sends a real prompt, not a simulated request. Obtain the payer's authorization first. It records a separate `verification` payment in the live database and never creates a router session. The request key is stored in `.local/live/payment-verification.json`; running the command again reuses that payment instead of charging again. Do not delete that file to retry an unresolved payment. Inspect the existing payment in the dashboard first.

A confirmed collection verifies authentication, STK initiation, provider confirmation, callback processing, and settlement. It does not verify speed limits, hotspot login, or router provisioning. Add the real router and plans, deploy `hotspot/login.html`, and test a genuine device purchase to validate paid internet access.
